2025 → 2026 / Engineering Growth

From writing code
to understanding systems.

A practical look at how my Odoo frontend, OWL, backend, debugging, architecture, and ownership evolved.

01 / The biggest change

The questions became
better.

2025

“How do I fix this?”

  • Start from the error or snippet
  • Focus on making the feature work
  • Debug the visible symptom
  • Ask for the implementation pattern
→
2026

“Why does this happen?”

  • Identify the system boundary
  • Understand lifecycle and dependencies
  • Look for the root cause
  • Choose an architecture, not only a patch
02 / Odoo Website Frontend

From QWeb implementation
to website engineering.

2025

QWeb & DOM

Worked heavily with QWeb conditions, template context, product cards, images, URLs, pricing, SVGs, publicWidget events and DOM interactions. The focus was getting the UI behavior correct.

2026

Website architecture

Started reasoning about snippet lifecycle, editor mode, asset loading, dynamic snippets, nested components, initialization timing and interactions between custom code and Odoo’s website editor.

Example

Dynamic snippets

Instead of treating an editor problem as a simple JS bug, the investigation reached double initialization, DOM mutation in edit mode, nested website-form behavior and snippet separation.

Impact

Better decisions

This makes frontend work safer: fewer fixes that solve one page while breaking the editor, other snippets, or future changes.

05 / Backend Growth

Frontend became stronger
because backend became stronger.

Controllers

Moved from simply consuming backend data to designing controller behavior, request types, pagination, sorting, filters, exports and response formats.

ORM & models

More comfortable reasoning about domains, records, permissions, computed/derived data, business rules and where validation belongs.

HTTP vs JSON-RPC

Worked through the distinction between binary downloads and JSON-RPC flows, including Odoo 19 request behavior and request-body handling.

Data flow

Dashboards now involve a full chain: database → ORM → controller → QWeb/JS → charts/UI → export, rather than treating frontend and backend as separate pieces.

06 / Backend — what changed in practice

Not just Python.
System thinking.

DatabaseUnderstand what data is needed and where it comes from.
ORMBuild the correct domain, records and business logic.
ControllerChoose the right route, request type and response.
FrontendConsume and transform data for the actual UI.
OutputCharts, pagination, exports and user actions become one flow.

Example: the company dashboard and Excel export work required thinking across the entire chain, including Odoo 19-specific request behavior.

07 / Debugging

The evolution of debugging

Before

Symptom-driven

  • “This error appears.”
  • Inspect the line
  • Try a correction
  • Test again
→
Now

Root-cause driven

  • What lifecycle is running?
  • Which layer owns the behavior?
  • What changed between Odoo versions?
  • Is another component initializing the same thing?
  • Can the fix create a second problem?
08 / Architecture & Quality

Fixing the problem
is no longer the finish line.

Separation of concerns

More attention to whether logic belongs in QWeb, JavaScript/OWL, a controller, a model, or an external service.

Version awareness

Odoo 19 behavior is not assumed to be identical to earlier versions. The request lifecycle, editor behavior and asset system can affect the correct solution.

Reusable solutions

More interest in patterns that can be reused across modules instead of one-off fixes.

Risk awareness

Consider side effects: editor mode, double initialization, DOM mutation, dependencies, performance and future maintenance.
